# Issuer certificate custody

First part of roadmap 2.2, Work Item WI-2026-11-22-001, testing ADR-0005. The issuer certificate has two uses, both fiscal: it signs documents and events (XML signature, `xmldsig#rsa-sha1`) and authenticates the client in the mutual TLS 1.2 connection to authorizers (MOC NF-e 7.0, CT-e 4.0, MDF-e 3.0b; NFS-e national APIs). Each row has automated tests in `ci/cert-custody/`: Linux runs in the OneDev job `cert-custody-linux`, Windows and macOS in GitHub Actions. The test certificates come from a test CA (`make-fixtures.sh`); none is ICP-Brasil.

Every store passed both uses from Rust: an RSA PKCS#1 v1.5 SHA-1 signature that verifies against the certificate, and a TLS 1.2 handshake with a server that requires a client certificate from the test CA (`rsa_pkcs1_sha256`). Negative controls (`tests/harness.rs`) show that a key not matching the certificate fails both.

| Store | OS | Exists | How | Key stays in the store | Removal | Limits |
| --- | --- | --- | --- | --- | --- | --- |
| Certificate store (A1) | Windows | Yes | PKCS#12 imported into the current user's `MY` store with the Microsoft Software Key Storage Provider and `NoExport` (`certutil -importpfx`); key from `CryptAcquireCertificatePrivateKey` (CNG only), signed with `NCryptSignHash` | `NCryptExportKey` refuses every private blob | Deleting the key (`NCryptDeleteKey`) and the certificate leaves nothing to sign with | Tested only with keys under the CNG software KSP, as the agent imports them; a certificate imported by other means into a legacy CSP was not tested. |
| Keychain (A1) | macOS | Yes | PKCS#12 imported with `security import -x -A`, partition list set for unsigned tools; identity found by certificate, signed with `SecKeyCreateSignature` | `SecKeyCopyExternalRepresentation` returns nothing | Deleting the identity removes certificate and key | Without `-A` and the partition list, a headless process would get an access prompt; a signed agent can be listed in the key's access control instead. |
| Agent's file store (A1) | Linux | Yes | PKCS#12 file in a directory owned by the agent's service account (0700, file 0600), parsed and signed in process | Another operating-system user cannot read the file | Deleting the file leaves nothing to sign with | Protection is file permissions only: root can read it, and the key is in the agent's memory while signing. Linux has no system key store. |
| PKCS#11 token (A3) | Linux, macOS, Windows | Yes | Module path plus the slot holding a token label (SoftHSM2 2.x; on Windows the 2.5.0 portable build); key and certificate found by label, signed with `CKM_SHA1_RSA_PKCS` / `CKM_SHA256_RSA_PKCS` | Key is `CKA_SENSITIVE`, not `CKA_EXTRACTABLE`, and its private exponent is refused | The user's tool (token driver), not Akela | One initialized module per process: finalizing it while another session is open crashes. Login is per token for the whole process. Real tokens' modules were not tested. |
| Smart card via the certificate store (A3) | Windows | Yes | Emulated PIV card (PivApplet on jCardSim behind the vsmartcard 0.11 virtual reader); key generated on the card, certificate from the test CA in slot 9a; Windows reaches it through the inbox PIV minidriver and the Smart Card KSP; the certificate is bound to the card key in the user's store (certificate propagation, or `certutil -repairstore` when propagation does not run on a headless runner); PIN given with `NCRYPT_PIN_PROPERTY` | The key never leaves the card | The user's tool (token driver), not Akela | Brazilian A3 tokens use their vendors' minidrivers, not the inbox PIV one; a real token is not tested. The virtual reader's test-signed driver installs without Windows test-signing mode once its certificate is trusted. |

## Gate result

Every store works for both uses on its operating system, so ADR-0005 stands and RFC-0002 C-CERTIFICATE-CUSTODY needs no change.
